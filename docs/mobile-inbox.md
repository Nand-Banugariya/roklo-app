# Mobile inbox and navigation

Approved direction: WhatsApp with business tools. Onboarding remains unchanged.

- Bottom navigation: Chats, Broadcast, Contacts. On Chats and Broadcast, the header shows a single button under the title. Connected: the connection name with its phone number beneath. Not connected: the name is hidden and only an amber "Not connected" pill with a breathing status dot shows ("Connecting…" while reconnecting); the name returns once the number is live. Tapping it opens the full numbers screen. Contacts keeps the compact Numbers switcher, whose count turns warning-toned when a number is offline.
- While numbers load, Chats shows only a centered spinner and no header status, so no chat placeholders, search or filters flash before the connection state is known.
- A number that has never been linked (no phone yet) shows a first-time "Link your WhatsApp" empty state with a Link WhatsApp action, and no header status pill, search, filters or reconnect dock.
- When a previously linked number is not live, the reconnect action lives in a persistent inverse dock in the thumb zone (where New chat normally sits): "Sales isn't connected · Chats are read-only until you reconnect" with Reconnect; its unplug icon is static. While reconnecting it shows a spinner and no action. Synced chats stay readable under a "Read-only · replies paused" divider and New chat is hidden. An empty offline inbox shows the static unplugged phone ↔ WhatsApp illustration ("Waiting for your phone"). The breathing loops are disabled under reduced motion. In a thread, the same dock replaces the composer. The dock is an inline, non-dismissable control, not a popup or sheet.
- Numbers, Menu, Alerts, accounts, workspaces, chat details and number linking are full Expo Router screens with Back navigation. No popup, bottom sheet, modal, or popover in the signed-in mobile flow. Settings selections and confirmations expand inline.
- Exactly one WhatsApp number is active. There is no combined/all-numbers inbox. The number name and phone appear beneath Chats. Remember manual selection by user and workspace; retain a selected disconnected number until the user switches it.
- WhatsApp numbers screen: inset rounded rows styled like "Connect another number", no full-width dividers. Each number shows a state-tinted phone tile, the name with its phone, "N chats · linked/last connected <date>" (`lastConnectedAt`), a daily usage bar ("sent / cap today" or "Paused"), a status pill (Connected / Disconnected / Not linked), an inline Reconnect or Link button, and a "…" button that opens the number's options inline under the row (one row at a time, no popover): Rename; Change visibility (Everyone / Teams and people / Only me, with team and people checklists for TEAM; shown to whoever added the number and to owners/admins); and Remove number with an inline confirmation. These use `PATCH` and `DELETE /w/:workspaceId/whatsapp/sessions/:id`, `GET /w/:workspaceId/teams` and `GET /workspaces/:workspaceId/members`. The active number comes first, tinted, with a check. "Connect another number" and "Manage numbers" rows follow. Phones are shown in international grouping (`+91 98765 43210`) via `numberPhone`.
- Chats and threads: per-contact avatar tones, bold unread previews, relative stamps (time, Yesterday, weekday, date), WhatsApp-style message grouping with day chips, optimistic sending (clock → tick, draft restored on failure), a jump-to-latest button, quick-start replies in empty threads and a floating composer.
- Threads sit on the web app's doodle wallpaper (`assets/images/chat-wallpaper*.webp`, light and dark), fixed behind the thread and composer as on WhatsApp mobile. `ChatWallpaper` lays the 2x tile out by hand at 513.5x412 because `resizeMode="repeat"` scales differently per platform. While a thread loads, `ThreadSkeleton` shows placeholder bubbles and a day chip on the wallpaper.
- The thread and composer rise with the keyboard on iOS and Android (`KeyboardScreen`): Reanimated's keyboard height, minus the bottom safe-area inset the app shell already reserves, pads the screen frame by frame. Android draws edge-to-edge, so `softwareKeyboardLayoutMode: "resize"` no longer shrinks the window, and KeyboardAvoidingView came out short by about the navigation bar. A device that does shrink the window has that shrink subtracted, so nothing is lifted twice. The inverted list keeps the latest message just above the composer.
- Media follows the web app's bubble: a lone video plays in the bubble with platform controls (first frame, play button and length until started; the corner button opens the full-screen viewer); 4+ photos/videos form a 2x2 album that opens the viewer. Audio and voice notes play inline with a seekable line and a 1x / 1.5x / 2x speed pill. One sound at a time (`utils/playback.ts`). A customer typing or recording a voice note shows a dots bubble (mic when recording) at the end of the thread. Recording and sending voice notes is not in the web app either; audio files can be attached.
- Message actions follow the web app's (React, Reply, Pin, Forward) the WhatsApp mobile way, with no menus or popovers: long press picks a message (the row tints; taps then add or drop more), the header turns into an action bar (Reply and Pin/Unpin for one message, Copy, Forward), and a quick-reaction row (👍 ❤️ 😂 😮 😢 🙏 and +) sits above the one picked message; + swaps the composer for the emoji list. Reactions are optimistic and toggle like WhatsApp (your own again removes it; tapping a chip reacts with it). Swipe right on a message to reply; the quote shows in the composer and is sent as `replyToMessageId`. Up to 3 pins show in a pinned bar that jumps to each in turn. Tapping the quote in a reply (or the pinned bar) jumps to the original message, paging back through older messages if it isn't loaded yet (up to 20 pages), centres it and highlights its row in yellow for 2 s (the web app's reveal: pages of 100, up to 20; bg-highlight/50 fading over 500 ms); a message it can't reach says "Couldn't find this message in the chat". Forward opens a full "Forward to…" screen (up to 10 messages into 25 chats; above 3 chats the API sends a paced broadcast). Android back clears the selection. Delete, star and message info aren't in the API.
- Chats show their WhatsApp profile picture (`GET /conversations/:id/picture`, proxied and cached for an hour) in the chat list, the chat header, Forward and chat details, falling back to coloured initials. Pictures are cached in memory per user and workspace, fetched four at a time as rows render (`services/picture-cache.ts`, as on the web app). In group chats each member's run of messages starts with their initials avatar and their name in its colour with their number beside it (the number alone when there's no name); later messages in the run keep the avatar's space. The API has no picture for individual group members.
- Going back and forth stays calm: the chat list refreshes quietly when you return (no spinner; only pull to refresh shows one), and chats read in the thread lose their unread badge at once. The last 20 opened chats and 12 lists are kept in memory (`services/inbox-cache.ts`), so a chat opened again shows its messages immediately and refreshes in the background; only a first open shows the skeleton. The thread skeleton's bubbles (text lines, one photo, a time stub) rise into place one after another; the chat list skeleton pulses. Both are still under reduced motion.
- Messages are stored on the phone in SQLite (`services/message-store.ts`, expo-sqlite), the web app's IndexedDB cache (`lib/inbox/message-cache.ts`) with the same logic: a chat paints its stored copy at once (the skeleton shows only while it's read, or when nothing is stored), then the API's newest page reconciles it (`replaceCachedWindow`: stored messages missing inside the page's window were deleted; a gap replaces the whole copy) and `pruneCache` trims to 100 messages per chat and 50 chats. Older pages, sends, socket messages, reactions and pins are written as they arrive; ticks only move forward (`patchCachedStatus`). Chats that aren't open stay current from the socket (`MessageStoreSync`). A removed number drops its chats (`deleteCachedNumber`), the full numbers list drops chats on numbers you no longer have (`keepCachedNumbers`), another user or workspace wipes the copy, and sign-out (or an expired session) deletes the database. Only server copies are stored, every failure falls back to the API, and a failed write stands the store down. The web build uses `message-store.web.ts`, which stores nothing (expo-sqlite on web is alpha). The store also keeps each chat's details so its header shows straight away.
- The composer ports the web app's: a card with Reply / Private note tabs (switching clears the draft), WhatsApp's style options (Bold, Italic, Strikethrough, Monospace) that appear inline above the text while words are selected, wrapping them in WhatsApp markers or removing a style already applied, attachment chips (system document picker, up to 5 files of 16 MB in WhatsApp's types, sent as repeated `files` fields), and a Send button that turns amber for notes. Notes need only a live number; admin-only groups allow notes only. An emoji button swaps the keyboard for an inline emoji panel (the web app's list: recents, groups, search, a backspace that removes a whole emoji); tapping the text box or the keyboard button brings the keyboard back, and Android back closes it. Templates, scheduling, @mentions and quoted replies are popovers on web and still need full-screen or inline mobile designs.
- Chat threads show the message skeleton until the API finishes checking history. An empty page with `backfilling: true` keeps the skeleton while history imports; polling checks every 2 seconds during that sync. Populated caches still show messages immediately. Empty caches are rechecked, and failures show an error with retry instead of the greeting. The “Say hello” state appears only after a successful, completed empty response.
- AI Rephrase sits beside Attach and opens a 256px-wide popup directly above the icon. The popup has padded labels, 40px rows and small 2px gaps between tones with all five tones visible. Rewrites stay in the draft for review, with Undo and Keep; cancellation and edits preserve newer drafts.
- Connect by phone number and linking code only. Never expose a QR flow.
- All chats is a conversation filter for the active number, not an account filter.
- Inbox is backed by workspace-scoped session and conversation endpoints from the reference app. Search is debounced, conversations are paginated and virtualized, responses are aborted on blur/filter changes, and returned conversation session IDs are checked. Threads verify their session before fetching messages or enabling replies.
- Live updates currently poll visible conversations every 15 seconds and open threads every 10 seconds, while the app is active. This is not a socket subscription.
- Full-screen module navigation preserves the existing routes. Contacts, Groups, Templates, Broadcast, Message activity and AI connections remain module entry screens for subsequent implementation. Alerts currently show connection health; campaign notifications require their own integration.

## Motion contract

- Touch feedback: scale 0.98 and the pressed colour while the finger is down, after a 100 ms press delay so a touch that becomes a scroll never highlights the row; both clear on release, also when the press opened another screen. No transition classes on pressables (an animated view keeps a removed inline style, so the pressed colour stuck). Reduced motion drops the scale.
- Main destinations and Menu: immediate changes. No entrance animation for menu choices.
- Detail/number screens: native stack transitions, 240 ms, disabled with reduced motion.
- No staggered list entrances, bouncing controls, animated layout dimensions, or competing focal animations.

## Validation

Run `yarn lint`, `yarn typecheck`, and `yarn test`. Messaging tests cover account selection, workspace/number scoping, bare response handling, authentication failures, linking-code requests and multipart replies. Device checks should cover keyboard behavior, Back navigation, switching numbers, large text and reduced motion.

With Expo web running on port 8090, `node scripts/verify-mobile-navigation.cjs --chat-loading` uses intercepted fixtures to check delayed loads, history import, populated and empty caches, genuinely empty chats, failed loads and retries without a greeting flash. It also checks the AI popup's dimensions and spacing at 320/390/768/1024/1440 widths, rewriting and Undo.

The dependency-free browser review is `node scripts/verify-mobile-navigation.cjs`, with Expo web running on port 8090 and Chrome installed. It intercepts every API request using isolated fixtures, checks navigation and a text reply, and saves screenshots/results under `.expo/mobile-review/`. It does not sign into or change a real account. It covers 320/390/768/1024/1440 widths, dark theme, reduced motion, empty/error/disconnected states, touch targets and the phone-linking form. Native keyboard behavior and real WhatsApp pairing still need a device check.

Touch feedback uses the shared Pressable (`src/components/ui/pressable.tsx`): `active:` classes are applied as inline styles from its own press events, after a 100 ms delay. System reduced motion drops the 0.98 scale. Do not wrap the Pressable in a custom Reanimated component that receives unresolved class names: the Android layout can lose its sizing, flex and positioning even when the web layout works. The stack requests 240 ms detail transitions, with immediate primary navigation and Menu.
